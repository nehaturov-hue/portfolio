Anti-Hallucination

The core innovation. Every claim in a compiled article must be traceable to a specific line in a specific source file. If a fact isn't in the log, it doesn't make it into the body. No exceptions. This is enforced at compile time by the worker agent itself.

entities/electronic.md
Sources
wikipedia-electronic.md, wikipedia-kraftwerk.md
Result
13 ungrounded claims REMOVED. Brian Eno, Tangerine Dream, Wendy Carlos, Pink Floyd: not present in source files
Survived
Only facts directly traceable to the two source files
Confidence
low. Sources provide strong Kraftwerk coverage but limited standalone electronic music history

Fact-Log Protocol

Each compilation produces a structured fact log. The compiled body can only contain claims from this log.

Fact Log electronic.md
1. [source: wikipedia-electronic.md] Electronic music employs electronic musical instruments, digital instruments, or circuitry-based music technology…
2. [source: wikipedia-kraftwerk.md] Kraftwerk formed in Düsseldorf in 1970 by Ralf Hütter and Florian Schneider…
3. [source: wikipedia-kraftwerk.md] Their synthesizer-based approach influenced the development of electronic music genres…
RULE: If a fact is not in the log, it does not go in the body. No exceptions.

Scope Creep

The most interesting failure mode. The system compiles accurately, but it doesn't know when to stop. Wikis grow organically, absorbing content that drifts progressively further from the original domain. Here's what actually happened.

Jobseek Wiki, by the Numbers

Started as a focused Dutch job market knowledge base.

  • 294 concept pages
  • 231 root-level pages
  • 7 entity pages
  • 9 company profiles

Content That Drifted In

  • The Hague. City demographics, government, international orgs
  • Catharina-Amalia, Princess of Orange. Full biography
  • Council of State Netherlands. Constitutional structure
  • Benelux political structure
  • ASML, Philips, KPN, ING, ABN AMRO, PostNL, DSV, CEVA Logistics: full profiles

Example: The Hague Page

title: The Hague type: entity tags: [market-nl, sector-government, sector-it] confidence: high raw_compiled: true "The Hague is the seat of government of the Netherlands… King Willem-Alexander resides at Huis ten Bosch…"

This page is technically tagged as a job market location. But the compilation pulled in government structure, royal residence info, and international organization details. The wiki's knowledge boundary expanded beyond its original scope: accurately, but uncontrollably.

The core problem: Wikis grow organically. The system has no mechanism to detect when content crosses domain boundaries, and no way to dynamically spawn new wikis for discovered domains. The compilation is accurate (every fact is source-grounded), but the scope is unbounded.

What's Next

The next evolution: a scope-boundary detection system that treats domain drift as a signal, not a bug.

  1. Monitor incoming content for domain drift using semantic similarity against existing wiki scope
  2. Classify each piece of content as in-scope, borderline, or out-of-scope
  3. Cluster out-of-scope content to identify emergent domains
  4. Propose new wiki instances with auto-generated SCHEMA.md from detected content patterns
  5. Migrate misclassified pages to appropriate wikis with full provenance preserved

Stack

Pure file-based knowledge management. No database, no API layer, no frontend framework. The entire system runs on markdown files, YAML frontmatter, and agent orchestration.

Orchestration

Hermes Agent. Multi-profile orchestration framework. Each wiki gets isolated cron, skills, and sessions. Profiles don't share state.

Profile Architecture

Each wiki maps to a Hermes profile with its own skills/, cron/, and memories/. Complete isolation between wiki instances.

Skill System

wiki-compile (orchestrator skill) delegates to wiki-compile-entity (worker skill) via task delegation. Each worker handles one article.

Scheduling

1-minute cron intervals with script pre-run for file discovery and LLM delegation for compilation. Fires continuously across all wikis.

Storage

Markdown files with YAML frontmatter. JSON for state tracking. Flat directory structure per wiki. Human-readable at every layer.

Dependencies

No database. No API. No frontend. No build step. Pure file-based knowledge management with agent-driven compilation.
